== 1. Overview

=== 1.1 Purpose

The Hexal Lua Language Server API SHALL provide a complete scripting interface for implementing Language Server Protocol (LSP) servers entirely in Lua.

A Lua-based language server SHALL be capable of implementing:

* Syntax analysis and parsing.
* Semantic analysis and type checking.
* Diagnostics, warnings, and hints.
* Completion and completion resolution.
* Hover documentation.
* Go-to-definition and go-to-declaration.
* Find references and workspace symbol search.
* Rename and refactoring.
* Code actions and quick fixes.
* Document formatting.
* Semantic tokens and syntax highlighting.
* Inlay hints and signature help.
* Workspace indexing and dependency tracking.
* File watching and incremental analysis.
* Custom JSON-RPC methods and protocol extensions.
* Virtual documents and generated source files.
* Cancellation, asynchronous processing, and progress reporting.

Implementations MUST NOT require modifications to Hexal's C# source code.

The API SHALL provide the infrastructure necessary to implement an LSP server while leaving language-specific parsing, semantic analysis, and language intelligence to Lua.

=== 1.2 Design principles

The implementation SHALL follow these principles:

. Hexal owns the LSP transport, JSON-RPC runtime, and editor integration.
. Lua owns language-specific behavior and analysis.
. Standard LSP methods SHALL be supported through a consistent handler API.
. Custom methods SHALL be supported without modifying the Hexal runtime.
. Document contents SHALL remain synchronized with unsaved editor buffers.
. Long-running analysis SHALL NOT block interactive editor operations.
. All protocol communication SHALL be validated and error-isolated.
. Plugin permissions SHALL govern filesystem and process access.
. The API SHALL support both small scripts and compiler-grade language servers.
. Advanced features SHALL be optional when they are not needed by a language server.

== 3. Server Creation and Configuration

=== 3.1 Creating a server

Signature:

[source,lua]
----
hexal.lsp.create_server(options) -> Server
----

The function SHALL create a server instance without starting it.

Example:

[source,lua]
----
local lsp = require("hexal.lsp")

local server = lsp.create_server({
    name = "example-language",
    version = "1.0.0",

    filetypes = {
        "example",
    },

    extensions = {
        ".example",
        ".ex",
    },

    root_markers = {
        ".git",
        "example.json",
    },
})
----

The options table SHALL support the following fields.

[cols="1,1,3",options="header"]
|===
|Field |Type |Description

|name
|string
|Required server identifier.

|version
|string
|Optional server version.

|filetypes
|array of strings
|Language identifiers supported by the server.

|extensions
|array of strings
|File extensions associated with the server.

|root_markers
|array of strings
|Files or directories used to discover a workspace root.

|initialization_options
|table
|Default initialization options.

|settings
|table
|Default server configuration.

|capabilities
|table
|Features to advertise.

|encoding
|string
|Preferred position encoding.

|trace
|string
|Initial trace level.

|limits
|table
|Execution and resource limits.

|permissions
|table
|Requested optional permissions.
|===

=== 3.2 Server lifecycle

A Server object SHALL expose:

[source,lua]
----
server:start() -> boolean
server:stop() -> boolean
server:exit(code)
server:state() -> string
server:name() -> string
server:client() -> Client
server:capabilities(options)
server:advertised_capabilities() -> table
server:register(method, handler)
server:notify(method, handler)
server:on(event, handler)
server:off(event, handler)
----

The lifecycle states SHALL include:

* created
* initializing
* running
* shutting_down
* stopped
* failed

Invalid lifecycle transitions SHALL return an error or raise a documented Lua error.

Calling stop repeatedly SHALL be safe.

The host SHALL release server-owned resources when a server stops.

=== 3.3 Lifecycle events

The following events SHALL be supported.

[source,lua]
----
server:on("initialize", function(params, ctx)
    -- Return initialization result.
end)

server:on("initialized", function(params, ctx)
    -- Initialization is complete.
end)

server:on("shutdown", function(params, ctx)
    -- Release resources.
end)

server:on("exit", function(code, ctx)
    -- Final cleanup.
end)

server:on("document_opened", function(doc, ctx)
end)

server:on("document_changed", function(doc, ctx)
end)

server:on("document_saved", function(doc, ctx)
end)

server:on("document_closed", function(doc, ctx)
end)

server:on("workspace_changed", function(event, ctx)
end)

server:on("configuration_changed", function(settings, ctx)
end)
----

Event names SHALL be documented and stable.

The host SHALL prevent exceptions in an event handler from terminating unrelated servers or the editor.

=== 3.4 Handler registration

Request registration:

[source,lua]
----
server:register(method, handler)
----

Notification registration:

[source,lua]
----
server:notify(method, handler)
----

Examples:

[source,lua]
----
server:register("textDocument/hover", function(params, ctx)
    return {
        contents = {
            kind = "markdown",
            value = "Example documentation.",
        },
    }
end)

server:notify("workspace/didChangeConfiguration",
    function(params, ctx)
        -- Reload configuration.
    end
)
----

Request handlers SHALL return a result or an explicit protocol error.

Notification handlers SHALL NOT produce JSON-RPC responses.

Duplicate registration SHALL have documented behavior. The default behavior SHOULD be to reject duplicate registrations unless an explicit replacement option is supplied.

=== 3.5 Handler context

Each handler SHALL receive a context object.

[source,lua]
----
ctx.server
ctx.client
ctx.documents
ctx.workspace
ctx.request_id
ctx.method
ctx.cancelled
ctx.progress
ctx.initialization_options
ctx.settings
----

The context SHALL expose the relevant document, workspace, cancellation, and client information.

Request-specific properties MAY be absent when they are not applicable.

The context SHALL be valid only for its documented lifetime. Plugins MUST NOT assume that a request context remains valid indefinitely.

== 4. LSP Protocol Runtime

=== 4.1 Protocol responsibilities

The native Hexal runtime SHALL implement:

* JSON-RPC message framing.
* Content-Length header processing.
* JSON serialization and deserialization.
* Request ID allocation and correlation.
* Incoming request routing.
* Notification routing.
* Standard error responses.
* Cancellation handling.
* Initialization and shutdown sequencing.
* Capability negotiation.
* Protocol tracing.
* Request timeout management.
* Validation of incoming and outgoing messages.

Lua plugins SHALL NOT need to implement transport framing or request correlation.

=== 4.2 JSON-RPC errors

The following standard errors SHALL be supported:

[source,lua]
----
hexal.lsp.protocol.error_codes.PARSE_ERROR
hexal.lsp.protocol.error_codes.INVALID_REQUEST
hexal.lsp.protocol.error_codes.METHOD_NOT_FOUND
hexal.lsp.protocol.error_codes.INVALID_PARAMS
hexal.lsp.protocol.error_codes.INTERNAL_ERROR
hexal.lsp.protocol.error_codes.SERVER_NOT_INITIALIZED
hexal.lsp.protocol.error_codes.REQUEST_CANCELLED
hexal.lsp.protocol.error_codes.CONTENT_MODIFIED
hexal.lsp.protocol.error_codes.REQUEST_FAILED
hexal.lsp.protocol.error_codes.SERVER_CANCELLED
----

Handlers SHALL be able to return explicit errors.

[source,lua]
----
return ctx:reject(
    hexal.lsp.protocol.error_codes.INVALID_PARAMS,
    "Invalid document position."
)
----

An error constructor SHOULD also be provided.

[source,lua]
----
local err = hexal.lsp.protocol.make_error(
    code,
    message,
    optional_data
)
----

The runtime SHALL distinguish between protocol errors, Lua exceptions, and ordinary nil results.

A nil result SHALL represent a valid empty result where permitted by the relevant LSP method.

=== 4.3 Outgoing requests

Signature:

[source,lua]
----
server:send_request(method, params, callback, options)
    -> RequestHandle
----

Example:

[source,lua]
----
server:send_request(
    "workspace/configuration",
    {
        items = {
            { section = "example" },
        },
    },
    function(result, err)
        if err then
            return
        end

        -- Apply returned configuration.
    end
)
----

The runtime SHALL correlate the response with the original request.

RequestHandle SHALL expose:

[source,lua]
----
handle:id()
handle:cancel()
handle:is_pending()
handle:result()
----

The result API MAY use callbacks, awaitable tasks, or both.

The runtime SHALL support request timeouts and cancellation.

=== 4.4 Outgoing notifications

Signature:

[source,lua]
----
server:send_notification(method, params)
----

Notifications SHALL NOT allocate a response expectation.

The runtime SHALL validate outgoing notification parameters where a schema is available.

=== 4.5 Custom protocol methods

The API SHALL support custom JSON-RPC methods.

[source,lua]
----
server:register("example/analyze", function(params, ctx)
    return {
        successful = true,
    }
end)
----

Custom methods SHALL use the same validation, error handling, cancellation, and tracing infrastructure as standard methods.

=== 4.6 Initialization

The runtime SHALL support the standard LSP initialization lifecycle.

During initialization, the server SHALL receive:

* Client process information.
* Client capabilities.
* Workspace root information.
* Workspace folders.
* Initialization options.
* Position encoding preferences.
* Trace configuration.

The server SHALL return its supported capabilities and server information.

The runtime SHALL prevent ordinary feature requests from being dispatched before initialization has completed.

=== 4.7 Protocol version

The initial implementation SHALL target the official Language Server Protocol specification version supported by the corresponding Hexal release.

The host SHALL document its supported LSP version and supported method set.

Unsupported methods SHALL fail predictably.

== 5. Document Management

=== 5.1 Document retrieval

The document API SHALL expose:

[source,lua]
----
hexal.lsp.documents.get(uri) -> Document|nil
hexal.lsp.documents.get_open(uri) -> Document|nil
hexal.lsp.documents.is_open(uri) -> boolean
hexal.lsp.documents.open_documents() -> iterator
hexal.lsp.documents.snapshot(uri) -> DocumentSnapshot|nil
----

Equivalent access SHALL be available through:

[source,lua]
----
ctx.documents:get(uri)
----

A Document object SHALL expose:

[source,lua]
----
doc.uri
doc.language_id
doc.version
doc.text
doc.line_count
doc.is_open
doc.is_dirty
doc.encoding
----

Properties SHALL be read-only unless the API explicitly documents a mutation method.

The text of an open document SHALL reflect its current editor buffer, including unsaved changes.

=== 5.2 Document operations

Required methods:

[source,lua]
----
doc:get_text() -> string
doc:get_line(line) -> string|nil
doc:get_range(range) -> string
doc:word_at(position) -> string|nil
doc:word_range_at(position) -> Range|nil
doc:position_to_offset(position) -> integer
doc:offset_to_position(offset) -> Position
doc:get_changes_since(version) -> array
doc:snapshot() -> DocumentSnapshot
doc:is_open() -> boolean
doc:is_dirty() -> boolean
----

Lines and positions SHALL use zero-based indexing for LSP interoperability.

Out-of-range behavior SHALL be documented and consistent.

=== 5.3 Position encoding

The implementation SHALL support UTF-16 position encoding.

UTF-8 and UTF-32 MAY also be supported.

The negotiated encoding SHALL be used consistently for:

* Character positions.
* Range calculations.
* Incremental edits.
* Diagnostics.
* Completion edits.
* Semantic tokens.
* Formatting.
* Navigation results.

The API SHALL distinguish character offsets from byte offsets.

It SHALL NOT assume that one UTF-8 byte corresponds to one LSP character.

=== 5.4 Document snapshots

The document subsystem SHALL support immutable snapshots.

[source,lua]
----
local snapshot = doc:snapshot()

snapshot.uri
snapshot.version
snapshot.text
snapshot.line_count
----

A snapshot SHALL remain internally consistent even if the underlying editor buffer changes.

Analysis results computed against an older version SHALL NOT silently overwrite newer results.

=== 5.5 Document synchronization

The runtime SHALL handle:

* textDocument/didOpen
* textDocument/didChange
* textDocument/didSave
* textDocument/didClose

The runtime SHALL maintain the document version and apply incremental changes in the correct order.

A malformed change SHALL be handled without corrupting the document state.

=== 5.6 Large document support

Document operations SHOULD avoid copying entire documents when a line or range is sufficient.

The implementation SHOULD support efficient access to:

* Individual lines.
* Small text ranges.
* Position-to-offset conversion.
* Offset-to-position conversion.
* Immutable snapshots.
* Incremental change history.

The implementation SHOULD permit documents containing millions of lines, subject to configured memory and runtime limits.

== 6. Workspace API

=== 6.1 Workspace operations

A Workspace object SHALL expose:

[source,lua]
----
workspace:root_uri() -> string|nil
workspace:folders() -> array
workspace:configuration(section) -> any
workspace:find_files(glob, options) -> Task
workspace:read_file(uri) -> Task
workspace:stat(uri) -> Task
workspace:watch(glob, callback) -> WatchHandle
workspace:index(options) -> Task
workspace:progress(title, callback) -> Task
----

Workspace access SHALL support projects with multiple root folders.

A server SHALL NOT assume that a workspace contains only one directory.

=== 6.2 Filesystem module

The filesystem module SHALL expose:

[source,lua]
----
local fs = require("hexal.fs")

fs.read_file(path)
fs.write_file(path, contents)
fs.exists(path)
fs.stat(path)
fs.realpath(path)
fs.join(...)
fs.dirname(path)
fs.basename(path)
fs.normalize(path)
fs.glob(pattern, options)
fs.mkdir(path, options)
fs.remove(path)
fs.rename(old_path, new_path)
----

Operations that can block on disk SHOULD have asynchronous variants.

Filesystem operations SHALL obey plugin permissions and host security policy.

File writes, deletion, and renaming SHALL NOT be permitted unless the plugin has the relevant permissions.

=== 6.3 File watching

File watching SHALL support:

* File creation.
* File modification.
* File deletion.
* Recursive directory watching where available.
* Glob-based filtering.
* Watch cancellation.
* Event coalescing.
* Resource cleanup.

The host SHOULD provide native file watching when supported and a polling fallback when necessary.

=== 6.4 Workspace indexing

The workspace index API SHOULD support:

[source,lua]
----
local index = require("hexal.index")

index:create(options)
index:add_file(uri, symbols)
index:remove_file(uri)
index:update_file(uri, symbols)
index:query_symbols(query, options)
index:query_references(symbol, options)
index:invalidate(uri)
index:clear()
----

Indexing SHALL support incremental updates.

The API SHALL permit a plugin to use its own index instead of the built-in index.

Persistent indexing MAY be supported, subject to plugin permissions.

== 7. Capability Negotiation

=== 7.1 Capability API

The capability module SHALL expose:

[source,lua]
----
hexal.lsp.capabilities.client() -> table
hexal.lsp.capabilities.server() -> table
hexal.lsp.capabilities.supports_client(path) -> boolean
hexal.lsp.capabilities.register(options) -> result
hexal.lsp.capabilities.unregister(options) -> result
----

The Server object SHALL support:

[source,lua]
----
server:capabilities(options)
server:advertised_capabilities() -> table
----

The host SHALL distinguish client capabilities from server capabilities.

=== 7.2 Capability declaration

Example:

[source,lua]
----
server:capabilities({
    text_document_sync = {
        open_close = true,
        change = "incremental",
        save = {
            include_text = false,
        },
    },

    hover = true,
    completion = true,
    definition = true,
    declaration = true,
    type_definition = true,
    implementation = true,
    references = true,
    document_symbols = true,
    workspace_symbols = true,
    rename = true,
    code_actions = true,
    formatting = true,
    range_formatting = true,
    signature_help = true,
    semantic_tokens = true,
    inlay_hints = true,
    folding_ranges = true,
    code_lens = true,
    document_links = true,
})
----

The host SHALL translate convenience names into the appropriate standard LSP capability structure.

Raw capability structures SHALL remain available for advanced features.

The host SHALL NOT advertise a feature merely because a Lua handler happens to be registered.

=== 7.3 Dynamic capabilities

Where supported by the negotiated protocol, servers SHALL be able to register and unregister capabilities dynamically.

The host SHALL validate registrations and communicate them to the client.

== 8. Diagnostics

=== 8.1 Diagnostics module

The diagnostics module SHALL expose:

[source,lua]
----
local diagnostics = require("hexal.lsp.diagnostics")

diagnostics.publish(uri, items)
diagnostics.clear(uri)
diagnostics.clear_all()
diagnostics.get(uri)
diagnostics.set(uri, namespace, items)
diagnostics.on_change(handler)
----

=== 8.2 Diagnostic structure

A diagnostic SHALL support the standard LSP fields:

[source,lua]
----
{
    range = {
        start = { line = 0, character = 0 },
        ["end"] = { line = 0, character = 5 },
    },

    severity = 1,
    code = "E001",
    codeDescription = {
        href = "https://example.invalid/errors/E001",
    },
    source = "example-language",
    message = "Unexpected token.",
    tags = {},
    relatedInformation = {},
    data = nil,
}
----

Optional fields SHALL be omitted when not applicable.

=== 8.3 Severity constants

[source,lua]
----
diagnostics.severity.ERROR
diagnostics.severity.WARNING
diagnostics.severity.INFORMATION
diagnostics.severity.HINT
----

=== 8.4 Namespaces

Diagnostics SHALL support namespaces so independent analyzers can manage separate diagnostic sets.

Publishing an updated set for one namespace SHALL NOT erase diagnostics owned by another namespace.

The runtime SHALL combine or publish the resulting diagnostics according to the supported LSP model.

=== 8.5 Version handling

Diagnostics MAY include document versions where supported.

Results produced from obsolete snapshots SHALL be discarded or handled according to a documented stale-result policy.

Closing a document SHALL clear diagnostics associated with that document unless the server explicitly retains workspace-level diagnostics through a supported mechanism.

== 10. Hover

The server SHALL support textDocument/hover.

Example:

[source,lua]
----
server:register("textDocument/hover", function(params, ctx)
    local doc = ctx.documents:get(params.textDocument.uri)
    local word = doc:word_at(params.position)

    if word == "greet" then
        return {
            contents = {
                kind = "markdown",
                value = "**greet(name)**\n\nReturns a greeting.",
            },
        }
    end

    return nil
end)
----

Hover results SHALL support:

* Markdown content.
* Plain-text content.
* Optional source ranges.
* Empty results.

The host SHALL respect the client's content-format capabilities.

The server SHALL support:

* textDocument/codeAction
* codeAction/resolve

Code actions SHALL support:

* Title.
* Kind.
* Diagnostics.
* Preferred-action status.
* Disabled-action reason.
* Workspace edits.
* Commands.

=== 12.2 Edit helpers

The edit module SHALL expose:

[source,lua]
----

== 13. Formatting

* textDocument/formatting

    tabSize = 4,
    insertSpaces = true,
    trimTrailingWhitespace = true,
}
----

Only standard protocol fields SHALL be transmitted to the client.

Additional plugin-specific formatting settings MAY be supplied through workspace configuration.

== 14. Semantic Tokens

=== 14.1 Supported methods

The runtime SHALL support:

* textDocument/semanticTokens/full
* textDocument/semanticTokens/full/delta
* textDocument/semanticTokens/range

=== 14.2 API

[source,lua]

== 16. Additional Language Features

The API SHALL support handler registration for the following methods when applicable to the negotiated protocol version.

=== 16.1 Folding ranges

* textDocument/foldingRange

API:

[source,lua]
----
hexal.lsp.folding_range.create(options)
----

== 17. Asynchronous Execution

=== 17.1 General requirements

The async subsystem SHALL support asynchronous operations without blocking editor input, rendering, or unrelated protocol handling.

[source,lua]
----
local async = require("hexal.async")

async.run(function()
    -- Asynchronous work.
end)
----

=== 17.2 Required API

[source,lua]
----
async.run(fn)
async.spawn(fn)
async.await(operation)
async.yield()
async.sleep(milliseconds)
async.cancel(task)
async.is_cancelled()
async.debounce(key, milliseconds, fn)
async.schedule(fn)
----

The exact task and awaitable representation SHALL be documented.

The runtime SHALL define error propagation, task ownership, cancellation behavior, and cleanup.

=== 17.3 Cancellation

Each cancellable LSP request SHALL receive a cancellation context.

The context SHALL expose a cancellation check.

[source,lua]
----
server:register("textDocument/references", function(params, ctx)
    local results = {}

    for item in expensive_reference_search(params) do
        if ctx.cancelled() then
            return nil
        end

        results[#results + 1] = item
    end

    return results
end)
----

Cancellation SHALL be cooperative for Lua code.

The runtime SHOULD terminate or isolate work that exceeds enforced execution limits, subject to safe runtime capabilities.

Cancellation of one request SHALL NOT automatically cancel unrelated tasks.

=== 17.4 Scheduling

The runtime SHOULD provide:

* Bounded concurrency.
* Priority for interactive requests.
* Cancellation propagation.
* Debouncing for document changes.
* Task timeouts.
* Queue limits.
* Background-task scheduling.
* Resource cleanup after errors.

=== 17.5 CPU isolation

The implementation SHALL document whether Lua execution is single-threaded.

CPU-intensive work SHOULD be offloaded to worker processes, isolated runtimes, or other supported mechanisms.

The host SHALL NOT promise parallel CPU execution merely because a Lua API supports asynchronous syntax.

== 18. Progress Reporting

The runtime SHALL support standard LSP progress reporting.

Handlers SHALL be able to create progress operations through the context.

[source,lua]
----
ctx.progress:begin("Indexing workspace", {
    percentage = 0,
})

ctx.progress:report({
    message = "Scanning source files",
    percentage = 50,
})

ctx.progress:finish("Indexing complete")
----

Progress APIs SHALL support cancellation when applicable.

Progress tokens SHALL be managed by the runtime.

The host SHALL respect client support for work-done progress.

== 23. Security and Permissions

=== 23.1 Plugin isolation

Language servers SHALL execute within Hexal's plugin security model.

The host SHALL provide documented controls for:

* Filesystem access.
* Workspace access.
* File modification.
* Process creation.
* Network access, if supported.
* Resource consumption.
* Logging and diagnostic output.

=== 23.2 Filesystem boundaries

Plugins SHALL NOT bypass filesystem permissions through URI conversion, symbolic links, path traversal, or alternative path representations.

The host SHALL validate access to resolved paths where permissions require it.

=== 23.3 Resource limits

The host SHOULD support configurable limits for:

* Memory usage.
* Lua execution time.
* Concurrent requests.
* Background tasks.
* Workspace indexing.
* Pending protocol requests.
* Diagnostic count.
* Completion result size.
* File-watching resources.

Exceeding a limit SHALL produce a documented error or cancellation rather than silently corrupting state.

=== 23.4 Failure isolation

A plugin failure SHALL NOT crash the editor.

The host SHALL isolate handler exceptions and report errors through the logging subsystem.

The host SHOULD provide a way to disable, restart, or unload a failed language server.

== 24. Performance Requirements

The implementation SHALL be designed for interactive use.

The following targets are initial engineering goals rather than unconditional guarantees.

[cols="2,2,3",options="header"]
|===
|Operation |Target |Notes

|Document lookup
|Under 1 ms
|For an already-open document under normal load.

|Cached hover
|Under 10 ms
|Excluding external or expensive analysis.

|Cached completion
|Under 20 ms
|Excluding client-side rendering.

|Incremental diagnostics
|Under 100 ms
|For ordinary edits in moderately sized files.

|Cancellation response
|Prompt
|Subject to cooperative Lua execution and host scheduling.

|Workspace indexing
|Background
|Must not block interactive editing.
|===

The implementation SHALL NOT guarantee these targets for arbitrary Lua scripts or arbitrarily large workspaces.

The runtime SHOULD optimize common document operations and minimize unnecessary allocation.

Implementations SHOULD include benchmarks for:

* Large documents.
* Rapid typing.
* Concurrent requests.
* Large workspaces.
* High-volume diagnostics.
* Semantic token deltas.
* Completion result generation.

== 25. Reference Server Example

The following example illustrates the intended API. It is a specification example and does not imply that every function already exists in a particular Hexal build.

[source,lua]
----
local lsp = require("hexal.lsp")
local diagnostics = require("hexal.lsp.diagnostics")

local server = lsp.create_server({
    name = "example-language",
    version = "1.0.0",
    filetypes = { "example" },
    extensions = { ".example" },
    root_markers = { ".git", "example.json" },
})

server:capabilities({
    hover = true,
    completion = true,
    definition = true,
    references = true,
    document_symbols = true,
    rename = true,
    code_actions = true,
    formatting = true,
})

server:on("initialize", function(params, ctx)
    return {
        capabilities = server:advertised_capabilities(),
        serverInfo = {
            name = "example-language",
            version = "1.0.0",
        },
    }
end)

server:on("document_changed", function(doc, ctx)
    local items = {}

    -- Replace this section with a parser and analyzer.
    local text = doc:get_text()

    if text:find("INVALID") then
        items[#items + 1] = {
            range = {
                start = { line = 0, character = 0 },
                ["end"] = { line = 0, character = 7 },
            },
            severity = diagnostics.severity.ERROR,
            source = "example-language",
            message = "Invalid token.",
        }
    end

    diagnostics.publish(doc.uri, items)
end)

server:register("textDocument/hover", function(params, ctx)
    local doc = ctx.documents:get(params.textDocument.uri)
    local word = doc:word_at(params.position)

    if word == "greet" then
        return {
            contents = {
                kind = "markdown",
                value = "**greet(name)**\n\nReturns a greeting.",
            },
        }
    end

    return nil
end)

server:register("textDocument/completion", function(params, ctx)
    return {
        isIncomplete = false,
        items = {
            {
                label = "greet",
                kind = 3,
                detail = "function greet(name)",
                insertText = 'greet("${1:name}")',
                insertTextFormat = 2,
            },
        },
    }
end)

server:register("textDocument/definition", function(params, ctx)
    -- Return a Location, LocationLink, or an empty result
    -- appropriate for the negotiated LSP method.
    return nil
end)

server:start()
----

== 26. Conformance Requirements

An implementation claiming full conformance with this specification SHALL satisfy the following requirements.

=== 26.1 Core conformance

* [ ] Lua can create and start an LSP server.
* [ ] The runtime implements JSON-RPC framing and message routing.
* [ ] The runtime supports initialization, shutdown, and exit.
* [ ] Lua can register arbitrary standard and custom methods.
* [ ] Open documents remain synchronized with editor buffers.
* [ ] Document positions respect the negotiated encoding.
* [ ] Requests support cancellation and error handling.
* [ ] Capabilities are negotiated correctly.
* [ ] Diagnostics can be published and cleared.
* [ ] Completion, hover, navigation, and references can be implemented in Lua.
* [ ] Workspace access respects plugin permissions.
* [ ] Handler errors do not crash the editor.

=== 26.2 Advanced conformance

* [ ] Workspace indexing and file watching are available.
* [ ] Code actions and workspace edits are supported.
* [ ] Formatting and rename are supported.
* [ ] Semantic tokens and token deltas are supported.
* [ ] Inlay hints and signature help are supported.
* [ ] Async execution and progress reporting are supported.
* [ ] Virtual documents and custom URI schemes are supported where configured.
* [ ] Resource limits and tracing are available.
* [ ] A testing framework can simulate LSP requests and document changes.

=== 26.3 Compatibility

The host SHALL document:

* Supported LSP specification version.
* Supported methods and structures.
* Supported position encodings.
* Lua runtime version.
* Async execution semantics.
* Filesystem and process permissions.
* Resource limits.
* Unsupported or partially supported features.

The host SHALL preserve backward compatibility for documented APIs within a stable major version.

Breaking API changes SHALL require a major version increment or an explicitly documented migration mechanism.

== 27. Recommended Implementation Order

=== Phase 1: Protocol foundation

. Implement JSON-RPC framing and serialization.
. Implement server lifecycle and handler registration.
. Implement initialize, initialized, shutdown, and exit.
. Implement document synchronization and snapshots.
. Implement cancellation and error handling.
. Implement basic capability negotiation.

Acceptance criterion: a Lua server can initialize and answer a hover request from Hexal.

=== Phase 2: Core language features

. Implement diagnostics.
. Implement completion and completion resolution.
. Implement hover.
. Implement definition and references.
. Implement document and workspace symbols.
. Implement rename and code actions.
. Implement formatting.

Acceptance criterion: a Lua plugin can provide a useful language server without modifying Hexal's source code.

=== Phase 3: Workspace and scalability

. Implement asynchronous filesystem access.
. Implement file watching.
. Implement workspace indexing.
. Implement incremental document updates.
. Implement progress reporting.
. Implement request prioritization and cancellation.
. Implement performance tracing.

Acceptance criterion: the server can analyze multi-file workspaces while the editor remains responsive.

=== Phase 4: Advanced protocol features

. Implement semantic tokens and delta caching.
. Implement inlay hints and signature help.
. Implement folding ranges and selection ranges.
. Implement code lenses and document links.
. Implement call and type hierarchy.
. Implement virtual documents and custom URI support.

Acceptance criterion: the API supports the major language intelligence features expected from a modern editor.

=== Phase 5: Production hardening

. Implement resource limits and plugin isolation.
. Implement the LSP test harness.
. Add protocol conformance tests.
. Add large-file and large-workspace benchmarks.
. Document all public modules and types.
. Establish stable API versioning.

Acceptance criterion: third-party authors can implement, test, distribute, and maintain complete Lua language servers independently of Hexal's release cycle.

== 28. Final Architectural Requirement

Hexal SHALL provide a language-server runtime, not merely a collection of helper functions.

The runtime SHALL own protocol transport, lifecycle, document synchronization, capability negotiation, cancellation, and safe editor integration.

Lua SHALL own language-specific parsing, analysis, diagnostics, completion, navigation, refactoring, and any custom language intelligence.

The API SHALL be layered so that a simple linter requires only a small subset of the modules, while a compiler-grade language server can access the complete feature set.

The final objective is that an author can implement and distribute a complete language server as a Lua plugin, without modifying Hexal's C# code or implementing the LSP transport independently.

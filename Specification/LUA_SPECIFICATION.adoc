HEXAL LUA PLUGIN API SPECIFICATION
=================================

1. OVERVIEW
-----------

Hexal shall expose a modular Lua API for plugins, backed by
a C# host and a native Lua runtime.

Plugins must interact with Hexal through documented API
modules rather than accessing internal editor classes.

Module namespace: hexal.<module>

Core modules:
  hexal.editor
  hexal.commands
  hexal.keymap
  hexal.ui
  hexal.events
  hexal.lsp
  hexal.config


2. hexal.editor
---------------

PURPOSE:
  Inspect and modify the active editor buffer.

FUNCTIONS:
  get_current_buffer()
    Return the active buffer identifier.

  get_text()
    Return the current buffer contents.

  get_line(line)
    Return the contents of a specified line.

  get_cursor()
    Return cursor line and column.

  set_cursor(line, column)
    Move the cursor.

  get_selection()
    Return the active selection, if any.

  insert_text(text)
    Insert text at the cursor.

  replace_range(start, finish, text)
    Replace a range of buffer contents.

RULES:
  - Use documented line/column indexing conventions.
  - Validate ranges before modifying buffers.
  - Integrate edits with undo/redo.
  - Do not expose internal buffer objects.


3. hexal.commands
-----------------

PURPOSE:
  Register named commands callable by users, plugins
  or other Hexal subsystems.

FUNCTIONS:
  register(name, callback, description)
    Register a Lua callback as an editor command.

  unregister(name)
    Remove a plugin-owned command.

  execute(name, ...)
    Execute a registered command.

EXAMPLE:
  hexal.commands.register("Hello", function()
      hexal.ui.message("Hello from Hexal")
  end)


4. hexal.keymap
---------------

PURPOSE:
  Bind key sequences to commands or Lua callbacks.

FUNCTIONS:
  map(keys, command, mode)
    Bind keys to a named command.

  map_callback(keys, callback, mode)
    Bind keys directly to a Lua callback.

  unmap(keys, mode)
    Remove a plugin-owned binding.

RULES:
  - Support configurable editor modes.
  - Detect or resolve conflicting bindings.
  - Allow users to override default bindings.


5. hexal.ui
-----------

PURPOSE:
  Provide controlled access to editor UI components.

FUNCTIONS:
  message(text)
    Display a status or informational message.

  warn(text)
    Display a warning.

  prompt(label, callback)
    Request user input asynchronously.

  select(items, callback)
    Display a selection menu.

  set_status(key, text)
    Set a plugin-owned status-bar entry.

RULES:
  - UI operations must execute on the editor thread.
  - Long-running work must not block the editor.


6. hexal.events
---------------

PURPOSE:
  Allow plugins to react to editor lifecycle events.

FUNCTIONS:
  on(event, callback)
    Subscribe to an event.

  off(subscription_id)
    Remove a subscription.

INITIAL EVENTS:
  buffer_opened
  buffer_saved
  buffer_changed
  buffer_closed
  cursor_moved
  editor_started
  editor_shutdown

RULES:
  - Pass documented event data to callbacks.
  - Avoid recursive event loops during edits.
  - Release subscriptions when a plugin unloads.


7. hexal.lsp
------------

PURPOSE:
  Provide a high-level interface to Language Server
  Protocol functionality implemented by the C# host.

FUNCTIONS:
  start(server_config)
    Start or attach to a configured language server.

  stop(server_name)
    Stop a managed language-server session.

  request(method, params, callback)
    Send an LSP request and deliver its result
    asynchronously.

  notify(method, params)
    Send an LSP notification.

  on_diagnostics(callback)
    Subscribe to diagnostic updates.

  go_to_definition()
    Navigate to the symbol definition.

  find_references()
    Find references to the symbol at the cursor.

RULES:
  - C# owns process management and JSON-RPC transport.
  - The host handles document synchronization.
  - Requests must support errors and cancellation.
  - Never block the UI while waiting for a response.


8. hexal.config
---------------

PURPOSE:
  Store and retrieve plugin-specific settings.

FUNCTIONS:
  get(key, default_value)
    Read a setting.

  set(key, value)
    Update a setting.

  save()
    Persist supported settings.

  get_all()
    Return the plugin's settings table.

RULES:
  - Namespace settings by plugin identifier.
  - Validate values against declared schemas.
  - Keep user configuration separate from plugin defaults.
  - Do not permit arbitrary writes to Hexal internals.


9. PLUGIN LIFECYCLE
-------------------

Each plugin shall have a manifest and Lua entry point.

Example layout:

  plugins/
    example/
      plugin.toml
      init.lua
      config.lua

Manifest example:

  name = "Example"
  version = "1.0"
  description = "What the plugin does"
  author = "Plugin Author"
  license = "MIT"
  entry = "init.lua"
  enabled = true

The author and license fields are optional metadata. They are shown in
the plugin manager together with the plugin's version, description,
commands, paths and load errors.

LIFECYCLE:
  1. Read and validate manifest.
  2. Create plugin execution context.
  3. Register approved API modules.
  4. Execute plugin entry point.
  5. Track commands, keymaps and subscriptions.
  6. Clean up plugin-owned resources on unload.

A plugin failure must not crash the editor.


10. IMPLEMENTATION REQUIREMENTS
-------------------------------

- Native Lua runtime; C# host compiled with Native AOT.
- Keep native Lua bindings behind a C# abstraction.
- Expose only documented functions to Lua.
- Validate all API arguments and return values.
- Convert Lua errors into plugin-scoped errors.
- Track ownership of registered resources.
- Document API version and compatibility policy.
- Treat plugins as potentially untrusted code;
  an in-process Lua runtime is not a security boundary.

DESIGN PRINCIPLE:
  C# owns editor state, native integration, concurrency
  and LSP transport. Lua owns plugin behaviour,
  customization and user-defined workflows.

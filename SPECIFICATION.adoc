HEXAL
=====

Project Type:
    Cross-platform, modal, terminal-based text editor.

Target Platforms:
    Linux
    macOS
    Windows

Primary Goal:
    Provide a highly responsive, keyboard-driven text editor capable of
    editing files containing millions of lines without noticeable lag.

Design Philosophy:
    Performance first.
    Modal editing.
    Minimal interface.
    Configurable languages, themes, formatters, and LSPs.
    Platform-independent core.
    No unnecessary dependencies.
    Never block the UI during expensive operations.


============================================================
1. CORE ARCHITECTURE
============================================================

The application MUST be divided into independent subsystems:

    Application
        |
        +-- Command Dispatcher
        |
        +-- Modal Input Engine
        |
        +-- Buffer Manager
        |       +-- Text Buffer
        |       +-- Undo / Redo
        |       +-- Cursor and Selection
        |       +-- Line Index
        |
        +-- Rendering Engine
        |       +-- Viewport
        |       +-- Syntax Highlighting
        |       +-- Themes
        |
        +-- File System
        |       +-- File Reading
        |       +-- File Writing
        |       +-- Wildcard Search
        |       +-- File Tree
        |
        +-- Configuration Manager
        |       +-- .hexcfg
        |       +-- .hexdef
        |
        +-- External Tool Integration
                +-- Formatters
                +-- Language Servers (LSPs)

All core functionality MUST be independent of the terminal UI library.

The UI MUST NOT depend on a specific operating system.

Platform-specific code MUST be isolated behind abstractions.


============================================================
2. PERFORMANCE REQUIREMENTS
============================================================

The editor MUST support files containing millions of lines.

The editor MUST avoid copying the entire file for ordinary edits.

The editor MUST NOT render the entire document on each frame.

Required behaviour:

    - Render only visible lines and required viewport margins.
    - Keep cursor movement independent of total file length where possible.
    - Maintain an efficient line index.
    - Update syntax highlighting incrementally.
    - Update only the affected viewport regions after edits.
    - Perform file searches incrementally or asynchronously.
    - Never block keyboard input while searching or highlighting.
    - Avoid allocating memory on every rendered character.
    - Avoid loading additional copies of the complete document.
    - Use buffered, efficient file I/O.
    - Use a scalable undo/redo representation.
    - Avoid full-document rescans after ordinary edits.

The text buffer MUST use a data structure designed for large editable
documents, such as a piece tree, piece table, or rope.

The implementation MUST select and document its buffer strategy.

Large-file operations MUST remain responsive, including:

    - Opening a large file.
    - Moving between distant lines.
    - Editing text near the beginning or end.
    - Searching for text.
    - Selecting large ranges.
    - Saving the document.
    - Resizing the terminal.

Expensive operations MUST run outside the UI input/rendering path.

The editor SHOULD support a configurable large-file mode that can disable
expensive syntax highlighting, diagnostics, and other optional processing.

The editor MUST measure and minimize:
    - Time to open a file.
    - Time to first render.
    - Cursor movement latency.
    - Edit latency.
    - Search latency.
    - Memory consumption.
    - Save latency.

Performance MUST be benchmarked against representative files containing
100,000, 1,000,000, and multiple millions of lines.


============================================================
3. COMMAND-LINE / EX COMMAND INTERFACE
============================================================

Commands are entered through a command prompt beginning with ':'.

Command parsing MUST support:
    - Command names.
    - Positional arguments.
    - Filenames containing spaces.
    - Quoted arguments where appropriate.
    - Useful error messages.
    - Unknown-command handling.

Commands MUST NOT crash the application when given invalid input.


------------------------------
:w
------------------------------

Save the current buffer to its associated file.

Requirements:
    - Write the current document contents to disk.
    - Report success or failure in the status bar.
    - Preserve the original file if saving fails where feasible.
    - Never silently discard unsaved changes.
    - Update the buffer's saved/modified state after successful saving.

If the buffer has no associated filename, report an error and direct the
user to provide a filename using an appropriate save-as mechanism.


------------------------------
:wq
------------------------------

Save the current buffer and quit.

Requirements:
    - Save MUST complete successfully before quitting.
    - If saving fails, remain in the editor.
    - If saving is impossible because no filename is assigned, remain
      in the editor.
    - Never discard unsaved changes silently.


------------------------------
:fmt
------------------------------

Format the current document using its configured formatter.

Requirements:
    - Resolve the active language.
    - Look up the formatter configured for that language.
    - Execute the formatter without blocking UI input.
    - Support configurable executable paths and arguments.
    - Support formatting through stdin/stdout where possible.
    - Support formatters that require temporary files.
    - Apply successful formatter output to the current buffer.
    - Preserve undo/redo behaviour.
    - Keep the document unchanged if formatting fails.
    - Display errors in the status bar.
    - If no formatter is configured, display an explicit error in
      the status bar.
    - Report missing executables, nonzero exit codes, and timeouts.
    - Never execute a shell command assembled from untrusted document
      contents.

Formatter execution MUST be configurable per language.

Formatting MUST NOT cause the editor to lose the user's cursor or
selection unnecessarily.


------------------------------
:cfg
------------------------------

Open the active .hexcfg configuration file for editing.

Requirements:
    - Open the actual configuration file in an editable buffer.
    - Create a default configuration if none exists.
    - Use normal editing commands to modify the file.
    - Do not overwrite the configuration automatically while the
      user is editing it.
    - Make the active configuration path discoverable.
    - Provide sensible defaults for missing optional settings.


------------------------------
:rcfg
------------------------------

Reload configuration from disk.

Requirements:
    - Re-read the active .hexcfg file.
    - Re-read language definitions referenced by the configuration.
    - Reload themes and formatter/LSP settings.
    - Validate all configuration before applying it.
    - Report parsing and validation errors in the status bar.
    - Preserve the previous valid configuration if reload fails.
    - Preserve open buffers, cursor positions, and undo histories.


------------------------------
:lang <language>
------------------------------

Set the active language for the current buffer.

Example:
    :lang cpp
    :lang python
    :lang rust

Requirements:
    - Resolve the language identifier against loaded .hexdef files.
    - Enable the corresponding syntax highlighting.
    - Associate the buffer with the language's configured formatter
      and LSP, if present.
    - Report an unknown language identifier.
    - Do not modify the file's contents merely by changing language.

Language auto-detection from filename associations SHOULD be supported.

An explicit :lang command MUST override automatic detection for the
current buffer until the user changes it or resets detection.


------------------------------
:sf <wildcard/pattern>
------------------------------

Open an interactive file-search modal.

Examples:
    :sf *.sh
    :sf src/*.cpp
    :sf **/*.h
    :sf test_*.py

Requirements:
    - Search filenames relative to the configured project root.
    - Support documented wildcard syntax.
    - Support recursive patterns if enabled by the pattern syntax.
    - Display matching filenames in a scrollable list.
    - Allow navigation using Up and Down arrow keys.
    - Support Page Up and Page Down.
    - Support Enter to open the selected file.
    - Support Escape to close the modal.
    - Update results asynchronously for expensive searches.
    - Display the number of matches when available.
    - Handle inaccessible directories and filesystem errors.
    - Avoid traversing configured ignored directories.
    - Do not freeze the UI during recursive searches.

The modal MUST clearly distinguish the selected result from other results.

Opening a file MUST respect unsaved-change protection.


------------------------------
:q
------------------------------

Quit the application.

Requirements:
    - If no buffers have unsaved changes, quit normally.
    - If unsaved changes exist, request confirmation.
    - Never silently discard unsaved changes.
    - Support cancellation of the quit operation.


------------------------------
:e <filename>
------------------------------

Open a file in an editor buffer.

Examples:
    :e main.cpp
    :e "src/my file.cpp"

Requirements:
    - Open existing files.
    - Allow new files to be created by opening a nonexistent filename,
      provided the parent directory is valid.
    - Resolve relative paths against the project root or documented
      working-directory rules.
    - Detect whether a file is already open and reuse its buffer.
    - Handle read-only files.
    - Handle permission errors and invalid paths.
    - Protect unsaved changes before replacing the current buffer.
    - Avoid loading duplicate full copies of an already-open file.


------------------------------
:g
------------------------------

Open an interactive file-tree modal.

Requirements:
    - Display the project directory hierarchy as a Unicode tree.
    - Use indentation and tree connectors, such as:

        project/
        ├── src/
        │   ├── main.cpp
        │   └── editor.cpp
        ├── include/
        │   └── editor.hpp
        └── README.md

    - Use the project root as the initial directory.
    - Support Up and Down to select entries.
    - Support Left and Right to collapse and expand directories.
    - Support Enter to open a file or expand a directory.
    - Support Escape to close the modal.
    - Support scrolling for large directory trees.
    - Avoid blocking the UI while scanning directories.
    - Exclude ignored directories according to configuration.
    - Handle symbolic links without infinite traversal.
    - Provide a useful representation if Unicode rendering is unavailable.

The tree MUST be navigable, not merely a static display.

The currently selected entry MUST be visibly highlighted.


============================================================
4. MODAL EDITING AND KEYBINDINGS
============================================================

The editor MUST support distinct modes:

    NORMAL MODE
    INSERT MODE
    SELECT MODE
    LINE SELECT MODE

The active mode MUST always be visible in the UI.

Keybindings MUST be configurable in the future, but the following
bindings are required initially.


------------------------------
NORMAL MODE
------------------------------

I
    Enter INSERT MODE at the current cursor position.

V
    Enter SELECT MODE.
    Begin a character-oriented selection at the cursor.

X
    Select the entire current line.
    Enter SELECT MODE with the full line selected.

GG
    Move the cursor to the first line of the document.

GE
    Move the cursor to the last line of the document.

GP
    Move to the previous cursor location.

Ctrl+C
    Toggle comments on the selected lines, or the current line if no
    selection exists.

    Requirements:
        - Resolve the comment syntax from the active .hexdef.
        - Support line comments and block comments where configured.
        - Preserve indentation.
        - Operate on all selected lines and all active cursors.
        - If no comment syntax is available, report an error.
        - Preserve selection and cursor position sensibly.

Shift+C
    Add a cursor on the next line at the same visual column, mirroring
    Helix's "copy selection on next line". Repeating the shortcut adds
    one cursor per line below the existing cursors.


------------------------------
INSERT MODE
------------------------------

    - Accept text input.
    - Support normal cursor movement.
    - Support deletion and insertion.
    - Escape returns to NORMAL MODE.
    - Edits MUST be undoable.
    - Text insertion MUST NOT require rebuilding the entire document.


------------------------------
SELECT MODE
------------------------------

    - Support character-oriented selection.
    - Arrow keys extend or adjust selection.
    - Selected text MUST be visually distinguishable.
    - Editing operations MUST act on the selection where appropriate.
    - Escape cancels selection and returns to NORMAL MODE.


------------------------------
LINE SELECT MODE
------------------------------

    - X selects the complete current line, including its line boundary
      when appropriate.
    - Arrow keys extend the selection by whole lines.
    - The selection MUST remain line-oriented.
    - Selection MUST work across very large documents.
    - Escape cancels selection and returns to NORMAL MODE.


============================================================
5. CURSOR AND NAVIGATION
============================================================

The editor MUST support:

    - Arrow-key cursor movement.
    - Horizontal and vertical movement.
    - Page Up and Page Down.
    - Home and End.
    - First and last line navigation.
    - Previous cursor location.
    - Selection-aware movement.
    - Scrolling without moving the cursor where appropriate.

The cursor MUST remain visible after navigation.

Vertical movement MUST preserve the preferred horizontal column when
possible.

Cursor positions MUST remain valid after edits and buffer changes.

The editor MUST maintain a navigation history sufficient for GP.

GP MUST move to the previously recorded cursor location, not simply
subtract one line.

The navigation history SHOULD avoid adding an entry for every individual
keystroke. It should record meaningful navigation events, such as jumps
between distant locations or files.


============================================================
6. TEXT BUFFER AND FILE HANDLING
============================================================

The buffer subsystem MUST provide:

    - Efficient insertion.
    - Efficient deletion.
    - Efficient range replacement.
    - Efficient line lookup.
    - Efficient cursor-to-line mapping.
    - Efficient line-to-cursor mapping.
    - Undo and redo.
    - Modified/clean state tracking.
    - Selection and range operations.
    - Large-file support.

The buffer MUST preserve text faithfully.

Requirements:
    - Detect and preserve line-ending conventions where possible.
    - Support LF and CRLF.
    - Handle a final line without a trailing newline.
    - Preserve encoding where supported.
    - Default to UTF-8 for new files.
    - Handle invalid UTF-8 according to a documented policy.
    - Avoid treating UTF-8 continuation bytes as independent characters
      when navigating or editing text.
    - Avoid corrupting files containing non-ASCII text.

The implementation MUST document its coordinate model:
    - Byte offsets.
    - Unicode code points.
    - Display columns.

These concepts MUST NOT be conflated.

Saving MUST be robust against partial writes and errors.

The implementation SHOULD use atomic replacement when appropriate,
while preserving file permissions and other relevant metadata where
possible.


============================================================
7. LANGUAGE DEFINITIONS: .hexdef
============================================================

Purpose:
    Define language metadata and syntax-highlighting rules.

The .hexdef format MUST be human-readable and JSON-like.

The format MUST have a documented schema and validation rules.

Example:

    {
        "id": "cpp",
        "name": "C++",
        "extensions": [".cpp", ".cc", ".cxx", ".hpp", ".h"],
        "lineComment": "//",
        "blockComment": {
            "start": "/*",
            "end": "*/"
        },
        "keywords": [
            "class",
            "struct",
            "namespace",
            "template",
            "typename",
            "public",
            "private",
            "virtual",
            "constexpr",
            "auto"
        ],
        "controlStatements": [
            "if",
            "else",
            "switch",
            "case",
            "for",
            "while",
            "do",
            "break",
            "continue",
            "return",
            "try",
            "catch",
            "throw"
        ],
        "types": [
            "int",
            "char",
            "bool",
            "float",
            "double",
            "void",
            "size_t"
        ],
        "constants": [
            "true",
            "false",
            "nullptr"
        ],
        "strings": {
            "quoteCharacters": ["\"", "'"],
            "escapeCharacter": "\\"
        },
        "comments": {
            "line": "//",
            "blockStart": "/*",
            "blockEnd": "*/"
        }
    }

This example illustrates the intended format. The implementation MUST
define one canonical schema and MUST NOT require duplicated fields such
as lineComment and comments.line to contain conflicting values.

Required language-definition capabilities:

    - Language identifier and display name.
    - Filename extensions and associations.
    - Keywords.
    - Control statements.
    - Types.
    - Constants and literals.
    - Line-comment syntax.
    - Block-comment syntax where applicable.
    - String delimiters and escape rules.
    - Optional additional highlighting categories.

Optional future capabilities:

    - Numeric literal patterns.
    - Preprocessor directives.
    - Operators.
    - Regular-expression-based token rules.
    - Multiline string rules.
    - Embedded languages.
    - Bracket matching rules.
    - Indentation rules.

Syntax highlighting MUST be incremental.

The syntax engine MUST NOT require a full-file rescan after each edit.

Language definitions MUST be data-driven. Adding a new language SHOULD
NOT require recompiling the editor.

Malformed definitions MUST produce useful validation errors.

Unknown or unsupported rules MUST be handled safely.


============================================================
8. CONFIGURATION: .hexcfg
============================================================

Purpose:
    Define editor settings, language associations, themes, formatters,
    language servers, project behaviour, and keybindings.

The .hexcfg file MUST use a documented JSON-like configuration format.

Example:

    {
        "version": 1,

        "project": {
            "root": ".",
            "ignoredDirectories": [
                ".git",
                "build",
                "node_modules",
                "vendor"
            ]
        },

        "languages": {
            "cpp": {
                "definition": "languages/cpp.hexdef",
                "extensions": [
                    ".cpp",
                    ".cc",
                    ".cxx",
                    ".hpp",
                    ".h"
                ],
                "formatter": {
                    "command": "clang-format",
                    "arguments": [
                        "--assume-filename={file}"
                    ],
                    "input": "stdin",
                    "output": "stdout"
                },
                "lsp": {
                    "command": "clangd",
                    "arguments": []
                }
            },

            "python": {
                "definition": "languages/python.hexdef",
                "extensions": [".py"],
                "formatter": {
                    "command": "black",
                    "arguments": ["-"],
                    "input": "stdin",
                    "output": "stdout"
                }
            }
        },

        "theme": "default",

        "themes": {
            "default": {
                "background": "#101010",
                "foreground": "#D0D0D0",
                "cursor": "#FFFFFF",
                "selection": "#404060",
                "keyword": "#C586C0",
                "controlStatement": "#569CD6",
                "type": "#4EC9B0",
                "string": "#CE9178",
                "comment": "#6A9955",
                "number": "#B5CEA8",
                "statusBar": "#202020",
                "error": "#F44747"
            }
        },

        "editor": {
            "tabWidth": 4,
            "useSpaces": true,
            "lineNumbers": true,
            "relativeLineNumbers": false,
            "largeFileMode": "automatic",
            "backupOnSave": true
        }
    }

The above schema is illustrative. The implementation MUST establish
a canonical schema and validate it consistently.

Configuration requirements:

    - Locate the active configuration using documented platform-specific
      configuration-directory conventions.
    - Support a project-level configuration where appropriate.
    - Allow a command-line option to override the configuration path.
    - Resolve relative paths predictably.
    - Validate configuration before applying it.
    - Report missing files and invalid settings.
    - Support defaults for omitted optional fields.
    - Never execute configuration values as arbitrary source code.
    - Preserve the last valid configuration after a failed reload.
    - Reload configuration without destroying open buffers.

Language associations MUST map filenames/extensions to .hexdef
definitions.

The configuration MUST support multiple themes.

Theme selection MUST update the UI without reopening documents.

Formatters and LSPs MUST be independently configurable per language.


============================================================
9. SYNTAX HIGHLIGHTING
============================================================

The rendering engine MUST support token categories defined by .hexdef.

At minimum:

    - Keywords.
    - Control statements.
    - Types.
    - Constants.
    - Strings.
    - Comments.
    - Numbers.
    - Default text.

Requirements:

    - Highlight only visible lines and necessary cached context.
    - Cache highlighting results.
    - Invalidate only affected regions where possible.
    - Support multiline constructs through lexer state carried between
      lines.
    - Avoid catastrophic performance from malformed definitions.
    - Fall back gracefully when syntax rules cannot be applied.
    - Disable or simplify highlighting automatically in large-file mode
      if necessary.

Regex rules, if supported, MUST be bounded or otherwise protected
against pathological execution times.


============================================================
10. LANGUAGE SERVER PROTOCOL (LSP)
============================================================

The editor MUST support configurable language servers through LSP.

Required initial capabilities:

    - Launch a configured language-server process.
    - Communicate using the LSP transport protocol.
    - Associate servers with applicable buffers.
    - Track document versions.
    - Send document open/change/close notifications.
    - Process diagnostics.
    - Display diagnostics without blocking the UI.
    - Shut down processes cleanly.

The architecture SHOULD allow future support for:

    - Completion.
    - Go to definition.
    - Hover information.
    - References.
    - Rename.
    - Signature help.
    - Code actions.

LSP functionality MUST be optional.

The editor MUST remain usable when no LSP is installed or configured.

Large-file mode SHOULD disable or limit LSP processing when appropriate.

LSP process failures MUST NOT crash the editor.


============================================================
11. FILE TREE AND WILDCARD SEARCH
============================================================

The filesystem subsystem MUST provide a shared project-root abstraction.

Wildcard search and the file tree MUST share:
    - Ignore rules.
    - Project root.
    - Path normalization.
    - Permission-error handling.
    - Symlink policy.

Wildcard syntax MUST be documented.

At minimum, support:
    *       Match zero or more characters within a path component.
    ?       Match one character within a path component.
    **      Match recursively across directory boundaries, if supported.
    []      Optional character classes.

Search results MUST be deterministic where practical.

Both the tree and search modal MUST remain navigable while the filesystem
is being scanned.


============================================================
12. STATUS BAR AND USER FEEDBACK
============================================================

The status bar MUST display relevant information, including:

    - Current mode.
    - Current filename.
    - Modified/clean state.
    - Current line and column.
    - Active language.
    - Active theme, if useful.
    - Current command or search progress.
    - Errors and warnings.

Errors MUST be concise and actionable.

Status messages MUST remain visible long enough to be read, unless
replaced by a newer message or dismissed by the user.

Long-running operations SHOULD display progress where appropriate.

The editor MUST distinguish errors from informational messages.


============================================================
13. UNDO AND REDO
============================================================

Undo/redo MUST be supported from the initial implementation.

Requirements:

    - Text edits MUST be reversible.
    - Range replacement MUST be undoable as one logical operation.
    - Formatter output SHOULD be undoable as one operation.
    - Commenting multiple lines SHOULD be undoable as one operation.
    - Large edits MUST NOT require full-document snapshots for every step.
    - Memory use MUST remain bounded by a documented retention policy.
    - Cursor and selection restoration SHOULD be supported.

The implementation MUST define how adjacent keystrokes are grouped into
logical undo operations.


============================================================
14. CROSS-PLATFORM REQUIREMENTS
============================================================

The application MUST compile and operate on:

    - Linux.
    - macOS.
    - Windows.

The implementation MUST isolate platform-specific behaviour, including:

    - Terminal input and output.
    - Terminal resize events.
    - Filesystem operations.
    - Process launching.
    - Path handling.
    - Environment-variable access.
    - Configuration directories.
    - File replacement semantics.
    - Unicode terminal output.

The application MUST NOT assume that:
    - Path separators are identical across platforms.
    - Executable names have identical extensions.
    - Every terminal supports true colour.
    - Every terminal has identical keyboard input behaviour.
    - UTF-8 output is always interpreted identically by the terminal.

The UI layer SHOULD use a cross-platform terminal abstraction or library.

All external commands MUST be launched using argument arrays or an
equivalent safe process API rather than shell-concatenated strings.

The build system MUST support reproducible builds on all target platforms.

The project MUST document dependencies and platform-specific build steps.

15. RELIABILITY AND DATA SAFETY
============================================================

The editor MUST:

    - Avoid silent data loss.
    - Handle disk-full errors.
    - Handle permission errors.

    - Recover the UI after an external command fails.

Where feasible, the editor SHOULD warn if the file has changed on disk
since it was loaded or last saved.

============================================================

Hexal is considered ready for its initial release when:

    [ ] It builds on Linux, macOS, and Windows.
    [ ] It opens, edits, and saves ordinary text files.
    [ ] It supports every required command.
    [ ] It supports every required mode and keybinding.
    [ ] It loads .hexcfg and .hexdef definitions.
    [ ] It switches themes and languages without restarting.
    [ ] It can format files using configured formatters.
    [ ] It reports missing formatters without crashing.
    [ ] It can browse wildcard search results.
    [ ] It can browse the Unicode file tree.
    [ ] It can integrate with configured LSPs.
    [ ] It protects unsaved changes.
    [ ] It supports undo and redo.
    [ ] It handles multi-million-line files.
    [ ] Ordinary edits do not require full-document copying.
    [ ] Ordinary rendering does not traverse the full document.
    [ ] Performance is measured and documented.
    [ ] Failed configuration reloads preserve the last valid settings.
    [ ] Files remain intact after failed saves or formatter execution.


HEXAL SUB-SPECIFICATION
======================
SPLIT WINDOWS, SETUP WIZARD, THEMES, CONFIGURATION MERGING,
AND COMMAND-LINE INTERFACE

Status:
    Proposed specification.

Compatibility:
    Must integrate with the main Hexal specification.
    Must remain language-agnostic.
    Must support Linux, macOS, and Windows.


============================================================
1. SPLIT WINDOWS
============================================================

1.1 OVERVIEW

Hexal MUST support multiple editor windows within a single terminal
instance.

Each window MUST contain an independent view of an editor buffer.

Windows MUST be arranged in a recursively splittable layout.

Supported split orientations:

    Horizontal split:
        Two windows stacked vertically.

    Vertical split:
        Two windows arranged side by side.

The implementation MUST distinguish between:
    - A buffer: the underlying document and its editing state.
    - A view: a window displaying a buffer, with its own cursor,
      viewport, scroll position, and selection state.
    - A pane: a region of the terminal assigned to a view.
    - A layout: the arrangement of panes within the terminal.

Multiple views MAY display the same buffer.

Editing a buffer MUST update every view displaying that buffer.

Cursor and viewport state SHOULD remain independent between views,
even when they display the same buffer.

The layout system MUST support more than two panes.


------------------------------------------------------------
1.2 COMMAND: :sv
------------------------------------------------------------

Purpose:
    Split the current pane vertically, creating a new pane to its right.

Example:

    +----------------------+----------------------+
    |                      |                      |
    |      Current         |       New            |
    |      Buffer          |       Buffer         |
    |                      |                      |
    |                      |                      |
    +----------------------+----------------------+

Requirements:

    - Divide the current pane into left and right panes.
    - Keep the existing view in the left pane.
    - Create a new view in the right pane.
    - Display the same buffer in the new view by default.
    - Preserve the original view's cursor, selection, and viewport.
    - Focus the newly created pane after splitting.
    - Resize both panes to fit the available terminal dimensions.
    - Draw a visible vertical divider between the panes.
    - Preserve all existing panes outside the split operation.

If the current pane is too small to split, the command MUST fail
gracefully and display an explanatory status message.

The split MUST NOT duplicate the entire underlying text buffer.


------------------------------------------------------------
1.3 COMMAND: :sh
------------------------------------------------------------

Purpose:
    Split the current pane horizontally, creating a new pane below it.

Example:

    +---------------------------------------------+
    |                                             |
    |                 Current                     |
    |                 Buffer                      |
    |                                             |
    +---------------------------------------------+
    |                                             |
    |                  New                        |
    |                 Buffer                      |
    |                                             |
    +---------------------------------------------+

Requirements:

    - Divide the current pane into upper and lower panes.
    - Keep the existing view in the upper pane.
    - Create a new view in the lower pane.
    - Display the same buffer in the new view by default.
    - Preserve the original view's cursor, selection, and viewport.
    - Focus the newly created pane after splitting.
    - Resize both panes to fit the available terminal dimensions.
    - Draw a visible horizontal divider between the panes.
    - Preserve all existing panes outside the split operation.

If the current pane is too small to split, the command MUST fail
gracefully and display an explanatory status message.

The split MUST NOT duplicate the entire underlying text buffer.


------------------------------------------------------------
1.4 PANE NAVIGATION
------------------------------------------------------------

The editor MUST provide keyboard navigation between panes.

Required behaviour:

    - Move focus to an adjacent pane.
    - Identify the currently focused pane visually.
    - Route keyboard input to the focused pane.
    - Preserve each pane's independent cursor and viewport.
    - Keep the active pane visible after terminal resizing.

The exact navigation keybindings MUST be configurable.

Suggested initial bindings:

    Ctrl+W, Left Arrow:
        Focus the pane to the left.

    Ctrl+W, Right Arrow:
        Focus the pane to the right.

    Ctrl+W, Up Arrow:
        Focus the pane above.

    Ctrl+W, Down Arrow:
        Focus the pane below.

If no pane exists in the requested direction, focus MUST remain
unchanged.

Navigation MUST work with nested split layouts.


------------------------------------------------------------
1.5 PANE RESIZING
------------------------------------------------------------

The layout system MUST support resizing individual panes.

Requirements:

    - Pane boundaries MUST be adjustable.
    - Pane sizes MUST be expressed as proportions or equivalent
      layout constraints rather than fixed terminal coordinates.
    - Resizing the terminal MUST recalculate the layout.
    - Pane dimensions MUST never become negative.
    - Panes MUST respect minimum usable dimensions where possible.
    - Layout constraints MUST be resolved predictably.

If the terminal becomes too small to display all panes, Hexal MUST
use a documented strategy, such as temporarily hiding inactive panes
or displaying a warning.

The application MUST NOT crash or corrupt the layout when panes
become too small.


------------------------------------------------------------
1.6 BUFFER MANAGEMENT IN SPLIT WINDOWS
------------------------------------------------------------

Each pane MUST be able to display a different buffer.

The existing :e <filename> command MUST open the requested file in
the focused pane.

Opening a file in one pane MUST NOT replace the buffers displayed
in other panes.

The implementation SHOULD provide a future command for explicitly
loading another buffer into the focused pane.

When two panes display the same buffer:

    - Text changes MUST appear in both panes.
    - Each pane MUST retain its own cursor position.
    - Each pane MUST retain its own viewport.
    - Selection state MUST remain independent.
    - Undo and redo MUST operate on the shared underlying buffer.

Closing a pane MUST NOT close a buffer still displayed elsewhere.

Unsaved-change protection MUST apply when closing a buffer or quitting
the application, not merely when changing pane focus.


------------------------------------------------------------
1.7 LAYOUT REPRESENTATION
------------------------------------------------------------

The layout MUST be represented by a tree or equivalent recursive
structure.

Conceptual example:

    Root
     |
     +-- Vertical Split
     |    |
     |    +-- Pane A
     |    |
     |    +-- Horizontal Split
     |         |
     |         +-- Pane B
     |         |
     |         +-- Pane C
     |
     +-- Pane D

The exact internal representation is implementation-defined.

Requirements:

    - Splitting one pane MUST NOT recreate unrelated panes.
    - Layout updates SHOULD affect only relevant layout branches.
    - Pane identifiers MUST remain stable until a pane is destroyed.
    - Focus MUST refer to a valid, existing pane.
    - Terminal resizing MUST recompute pane rectangles.
    - The layout system MUST avoid unnecessary full-screen redraws.

The layout system MUST remain independent of the text buffer
implementation.

2. SETUP WIZARD
============================================================

2.1 COMMAND: hexal setup

Purpose:
    Launch a user-friendly interactive setup wizard for initial
    configuration and subsequent preference changes.

The wizard MUST work on Linux, macOS, and Windows.

The wizard MUST be accessible without requiring the user to manually
edit configuration files.

The wizard MUST create or update the user's .hexcfg configuration.

The wizard SHOULD be usable by someone unfamiliar with Hexal's
configuration format.


------------------------------------------------------------
2.2 WIZARD ENTRY
------------------------------------------------------------

When the user runs:

    hexal setup

Hexal MUST launch an interactive terminal-based wizard.

The wizard MUST:

    - Explain each configuration section.
    - Support keyboard navigation.
    - Display available options clearly.
    - Provide sensible defaults.
    - Allow users to move backward and forward between steps.
    - Validate input before proceeding.
    - Support cancellation without modifying the existing configuration.
    - Summarize proposed changes before saving.
    - Explain where the configuration will be written.

If a valid configuration already exists, the wizard SHOULD load it
and use its values as the initial selections.


------------------------------------------------------------
2.3 CONFIGURATION STEPS
------------------------------------------------------------

The wizard MUST include the following sections.

STEP 1: GENERAL PREFERENCES

    - Configuration directory.
    - Default project root behaviour.
    - Default tab width.
    - Spaces versus tabs.
    - Line-number display.
    - Relative line numbers.
    - Large-file mode.
    - Backup-on-save preference.

STEP 2: THEME SELECTION

    - Display available installed themes.
    - Preview theme colours where supported.
    - Allow selection of a theme.
    - Provide a built-in default theme.
    - Explain how additional themes can be installed.

The preview SHOULD demonstrate:

    - Background and foreground.
    - Cursor.
    - Selection.
    - Keywords.
    - Strings.
    - Comments.
    - Types.
    - Status bar.
    - Errors and warnings.

The selected theme MUST be previewable before the configuration
is saved.

STEP 3: LANGUAGE SUPPORT

    - Display discovered language definitions.
    - Allow users to enable or disable language associations.
    - Show associated file extensions.
    - Explain that .hexdef files define language highlighting rules.
    - Allow users to select a default language where appropriate.

STEP 4: FORMATTERS

    - Display formatter settings for each configured language.
    - Allow users to configure executable paths and arguments.
    - Offer detection of commonly installed formatter executables.
    - Allow users to skip formatter configuration.
    - Provide a test option for configured formatters.

Formatter testing MUST NOT overwrite user files.

STEP 5: LANGUAGE SERVERS

    - Display LSP configuration for each applicable language.
    - Allow users to configure executable paths and arguments.
    - Offer detection of commonly installed language servers.
    - Allow users to skip LSP configuration.
    - Provide a basic connection/startup test where feasible.

STEP 6: KEYBINDINGS

    - Display default keybindings.
    - Allow users to review them.
    - Allow users to customize supported bindings.
    - Detect conflicting bindings.
    - Provide a restore-defaults option.

STEP 7: SUMMARY AND SAVE

    - Display a summary of selected preferences.
    - Show the destination .hexcfg path.
    - Validate the complete configuration.
    - Ask for confirmation before writing changes.
    - Save the configuration safely.
    - Report success or failure.
    - Offer to launch Hexal using the new configuration.


------------------------------------------------------------
2.4 SETUP WIZARD SAFETY
------------------------------------------------------------

The setup wizard MUST NOT:

    - Overwrite configuration without user confirmation.
    - Delete existing language definitions.
    - Replace custom themes without confirmation.
    - Execute formatter or LSP commands merely because they appear
      in a configuration file.
    - Require administrator privileges for ordinary user configuration.
    - Leave the configuration partially written after a failed save
      where atomic replacement is available.

The wizard MUST distinguish between:
    - A setting that is not configured.
    - A setting that is configured but unavailable.
    - A setting that has been tested successfully.

If an executable is missing, the wizard MUST explain the problem
without making setup fail entirely.

The wizard SHOULD support saving partial configurations when optional
components are unavailable.

3. THEME INSTALLATION
============================================================

3.1 COMMAND: hexal install-theme <file>

Purpose:
    Install a theme definition from a .hexcfg file.

Example:

    hexal install-theme sometheme.hexcfg

The command MUST install the supplied theme into the user's theme
directory.

The exact theme directory MUST follow documented platform-specific
configuration conventions.

Requirements:

    - Accept a path to a .hexcfg file.
    - Validate the configuration format.
    - Verify that the file contains a valid theme definition.
    - Extract or identify the theme's declared name and identifier.
    - Reject configurations that do not contain an installable theme.
    - Reject malformed or invalid colour values.
    - Prevent path traversal outside the theme installation directory.
    - Avoid overwriting an existing theme silently.
    - Display a clear success or error message.
    - Work without administrator privileges under normal conditions.

If the theme already exists, Hexal MUST ask for confirmation before
replacing it, unless an explicit overwrite option is implemented.

A theme installation MUST NOT silently replace the active editor
configuration.

The command MUST NOT execute arbitrary code from the supplied file.


------------------------------------------------------------
3.2 THEME FILE FORMAT
------------------------------------------------------------

Theme definitions MUST be compatible with the .hexcfg configuration
format.

A theme-only file SHOULD contain a dedicated theme section.

Example:

    {
        "themeDefinition": {
            "id": "sometheme",
            "name": "Some Theme",
            "author": "Theme Author",
            "version": 1,

            "colours": {
                "background": "#101010",
                "foreground": "#D0D0D0",
                "cursor": "#FFFFFF",
                "selection": "#404060",
                "keyword": "#C586C0",
                "controlStatement": "#569CD6",
                "type": "#4EC9B0",
                "string": "#CE9178",
                "comment": "#6A9955",
                "number": "#B5CEA8",
                "statusBar": "#202020",
                "error": "#F44747",
                "warning": "#D7BA7D"
            }
        }
    }

The example is illustrative. The implementation MUST define a single
canonical schema.

Theme files MUST support a documented set of colour roles.

Unknown optional colour roles SHOULD be ignored safely.

Missing required colour roles MUST use documented defaults or cause
validation failure, according to the schema.

Theme installation MUST NOT alter language associations, formatter
settings, LSP settings, or keybindings.


------------------------------------------------------------
3.3 THEME DISCOVERY
------------------------------------------------------------

Hexal MUST discover installed themes when loading configuration.

The editor MUST support:

    - A built-in default theme.
    - User-installed themes.
    - Theme selection through .hexcfg.
    - Theme preview through the setup wizard.
    - Theme changes without restarting the editor, where feasible.

If a configured theme is missing or invalid, Hexal MUST fall back
to the built-in default theme and report the problem.

Installed themes MUST be identifiable by stable IDs, not only by
display names or filenames.


============================================================
4. CONFIGURATION MERGING
============================================================

4.1 COMMAND: hexal merge-config <file>

Purpose:
    Merge settings from an external .hexcfg file into the user's
    active configuration.

Example:

    hexal merge-config someconfig.hexcfg

This command is intended to simplify sharing and distributing
configuration presets.

The source configuration MUST be validated before merging.

The command MUST NOT replace the entire active configuration by
default.


------------------------------------------------------------
4.2 MERGE BEHAVIOUR
------------------------------------------------------------

Hexal MUST merge the imported configuration with the active
configuration using deterministic rules.

Default rules:

    - Settings absent from the imported configuration remain unchanged.
    - Settings supplied by the imported configuration replace existing
      values for the same scalar setting, subject to conflict handling.
    - Imported language definitions are referenced only if valid and
      available, or if they are explicitly included and installed by
      a separately documented mechanism.
    - Theme selection may be imported if the referenced theme exists.
    - Theme definitions are not installed automatically unless the
      imported file explicitly contains a theme-installation payload.
    - Formatter and LSP settings may be imported but MUST NOT execute
      automatically during the merge.
    - Existing unrelated settings MUST be preserved.

Array-merging behaviour MUST be documented explicitly.

For example, language extension arrays MUST NOT be accidentally
concatenated if doing so would create duplicate or contradictory
associations.

The merge algorithm MUST be deterministic and repeatable.


------------------------------------------------------------
4.3 MERGE CONFLICTS
------------------------------------------------------------

If imported values conflict with existing values, Hexal MUST follow
a documented policy.

The initial implementation SHOULD support:

    Default:
        Imported values override matching settings.

    Optional future mode:
        Existing values take precedence.

    Optional future mode:
        Interactive conflict resolution.

The command SHOULD provide a preview of changed settings before
applying them.

If interactive conflict resolution is not supported, the command
MUST clearly state which precedence policy will be used.

Example output:

    Hexal configuration merge

    Source:
        someconfig.hexcfg

    Destination:
        ~/.config/hexal/hexal.hexcfg

    Changes:
        Theme: default -> sometheme
        Editor.tabWidth: 4 -> 2
        Languages: 3 settings updated

    Apply these changes? [y/N]


------------------------------------------------------------
4.4 MERGE SAFETY
------------------------------------------------------------

The merge operation MUST:

    - Validate the source configuration.
    - Validate the resulting merged configuration.
    - Preserve the active configuration if validation fails.
    - Avoid partial writes.
    - Create a backup where configured.
    - Avoid following malicious paths from imported configuration.
    - Avoid executing imported commands.
    - Report every failure clearly.

If no active configuration exists, Hexal MUST create a valid default
configuration and merge the supplied settings into it.

The operation MUST NOT delete user-installed themes, language
definitions, or unrelated files.

Relative paths in imported configurations MUST follow documented
resolution rules. They MUST NOT be interpreted unpredictably relative
to whichever directory happens to be active.

5. COMMAND-LINE HELP
============================================================

5.1 COMMAND: hexal --help

Purpose:
    Display concise command-line usage information and exit
    successfully.

The help output MUST work without launching the interactive editor.

It MUST NOT require a terminal capable of advanced Unicode or
true-colour rendering.

Example:

    Hexal - Modal Text Editor

    Usage:
      hexal [options] [file...]
      hexal setup
      hexal install-theme <file>
      hexal merge-config <file>

    Options:
      --help, -h          Show this help message
      --version           Show version information
      --config <file>     Use a specific configuration file
      --no-config         Start without loading user configuration

    Editor commands:
      :w                  Save the current buffer
      :wq                 Save and quit
      :q                  Quit
      :e <file>           Open a file
      :fmt                Format the current document
      :cfg                Open configuration
      :rcfg               Reload configuration
      :lang <language>    Set the current language
      :sf <pattern>       Search filenames
      :g                  Open the file tree
      :sv                 Split the current pane vertically
      :sh                 Split the current pane horizontally

    Keybindings:
      I                   Enter Insert Mode
      V                   Enter Select Mode
      X                   Select the current line
      Ctrl+C              Toggle comments on selected lines
      Shift+C             Add a cursor on the next line
      GG                  Go to the first line
      GE                  Go to the last line
      GP                  Go to the previous location

    Documentation:
      See the installed documentation or project documentation
      for complete usage instructions.

    Exit status:
      0                   Help displayed successfully


------------------------------------------------------------
5.2 HELP REQUIREMENTS
------------------------------------------------------------

The help command MUST:

    - Print usage information to standard output.
    - Exit with status code 0.
    - Avoid initializing the terminal UI.
    - Avoid loading language servers or starting external processes.
    - Avoid modifying configuration files.
    - Remain available if the user configuration is malformed.

Help text MUST remain synchronized with the actual command-line
interface.

The command-line parser MUST distinguish between:
    - Global command-line options.
    - Subcommands.
    - Filenames.
    - Editor-internal commands.

Unknown command-line options MUST produce an actionable error and
a nonzero exit status.

The --help option MUST take precedence over ordinary initialization
failures that are irrelevant to displaying help.


============================================================
6. COMMAND-LINE DISPATCH
============================================================

Hexal MUST distinguish between launching the editor and executing
standalone subcommands.

Examples:

    hexal
        Launch the editor.

    hexal main.cpp
        Launch the editor and open main.cpp.

    hexal main.cpp README.md
        Launch the editor with the supplied files.

    hexal setup
        Launch the setup wizard.

    hexal install-theme sometheme.hexcfg
        Install a theme and exit.

    hexal merge-config someconfig.hexcfg
        Merge configuration and exit.

    hexal --help
        Display help and exit.

The command-line dispatcher MUST execute standalone subcommands
before initializing the interactive editor.

Standalone subcommands MUST return meaningful process exit codes.

Suggested exit codes:

    0   Success.
    1   General failure.
    2   Invalid arguments or usage.
    3   Configuration validation failure.
    4   File or filesystem operation failure.

The exact codes MAY differ, but MUST be documented and used
consistently.

    [ ] :sh creates a lower pane.
    [ ] New panes display the same buffer by default.
    [ ] Panes can display different buffers.
    [ ] Editing a shared buffer updates all its views.
    [ ] Cursor and viewport state remain independent.
    [ ] Pane focus works with nested splits.
    [ ] Terminal resizing recalculates the layout.
    [ ] Too-small terminals are handled safely.
    [ ] Closing one pane preserves buffers shown elsewhere.

SETUP WIZARD

    [ ] hexal setup launches independently of the editor.
    [ ] Users can configure themes and editor preferences.
    [ ] Users can configure languages, formatters, and LSPs.
    [ ] Invalid settings are detected before saving.
    [ ] Cancellation preserves the previous configuration.
    [ ] Saving creates a valid .hexcfg file.
    [ ] The wizard works on all supported platforms.

THEME INSTALLATION

    [ ] hexal install-theme accepts a .hexcfg theme file.
    [ ] Invalid theme files are rejected.
    [ ] Existing themes are not overwritten silently.
    [ ] Installed themes become discoverable.
    [ ] Installation does not modify unrelated settings.
    [ ] No imported code is executed.

CONFIGURATION MERGING

    [ ] hexal merge-config merges settings deterministically.
    [ ] Unrelated settings remain unchanged.
    [ ] Conflicting values follow the documented policy.
    [ ] Invalid merged configurations are rejected.
    [ ] Failed merges preserve the previous configuration.
    [ ] No imported commands are executed.
    [ ] Existing themes and language definitions remain intact.

COMMAND-LINE HELP

    [ ] hexal --help prints usage information.
    [ ] It exits with status code 0.
    [ ] It does not launch the editor.
    [ ] It works without valid user configuration.
    [ ] It lists all implemented standalone commands.
    [ ] It lists all required editor commands and keybindings.

CROSS-PLATFORM

    [ ] All functionality builds on Linux.
    [ ] All functionality builds on macOS.
    [ ] All functionality builds on Windows.
    [ ] Configuration paths follow platform conventions.
    [ ] Paths containing spaces are handled correctly.
    [ ] Unicode filenames are handled correctly.
    [ ] Filesystem and process errors are handled safely.
